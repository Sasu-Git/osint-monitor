# Situation creation hold-out: pre-registration

Written 2026-09-29, before any hold-out data is inspected.

## Frozen implementation

- Principal actors: `cb32ea8` (PR #17).
- Situation creation: `c6dc1de` on `feat/situation-coverage`.
  - Candidate policy: `create_by: actor_pair`, `create_min_similarity: 0.40`.
  - Seeds, membership thresholds, arbiter, embeddings and naming are unchanged.
- The 0.40 threshold was chosen on the frozen clustering benchmark (10 windows) and inspected on
  the 2026-09-25 to 09-29 live events. Both are development data.
- Tooling: `evaluations/situations/holdout_tool.py` (commit `dbdecf9`, plus the labelling rule
  below).

## Hold-out window

- **2026-09-29 12:00 UTC to 2026-10-03 12:00 UTC**, 4 days, end exclusive. It will not be extended
  if recurrence is sparse.
- Collection: the daemon runs unchanged.
- Keep-awake: an external OS keep-awake (`SetThreadExecutionState`, WMI-launched, PID 33136) holds
  until 2026-10-03 13:00 UTC. The keep-awake does not protect against a manual sleep, lid
  close, reboot or power loss.
- Any collection gaps are recorded from log metadata before labelling.

## Procedure

1. After 2026-10-03 12:00 UTC, take a SQLite backup-API snapshot copy of the daemon DB (the DB
   itself is never written). Then run
   `holdout_tool.py freeze --start 2026-09-29T12:00 --end 2026-10-03T12:00`, which writes the
   developments with a SHA-256 and commits them.
2. Generate the blind label sheet with `holdout_tool.py sheet`. It lists every pair of
   developments sharing a canonical principal-actor pair, shuffled. It shows titles, leads,
   sources and times only: no candidate situations, similarities, recurrence counts, decisions
   or thresholds.
3. A separate agent labels each pair `SAME_SITUATION` / `DIFFERENT_SITUATION` / `AMBIGUOUS`.
   - A situation is one persistent geopolitical state of affairs. It is broader than a
     development or storyline.
   - **A coherent multi-day event (visit, summit, papal visit, disaster response) is not
     SAME_SITUATION by that fact alone.**
4. Freeze the labels (`freeze-labels`, SHA-256) and commit them before scoring.
5. One scored replay (`score`), after seed matching:
   - A: exact actor set;
   - B: actor pair >= 0.40;
   - diagnostic only, not selectable: actor pair >= 0.50.

   Seed assignments are reported separately.

## Reported per policy

For each policy the report covers:

- situations created, and developments assigned through creation;
- correct assignments, false joins, false situation creations, missed coherent recurring
  situations, and ambiguous cases;
- for broad pairs (US-China, US-Iran, Russia-Ukraine, Israel-Iran and others present): the
  founding pair and developments, similarities, domains, later members, and any false join.

## Decision rule (fixed now)

Exactly one of:

- **ENABLE ACTOR-PAIR CREATION**, only if all of these hold:
  - situation identity precision is high on the hold-out;
  - false situation creation is rare;
  - broad pairs do not systematically collapse unrelated storylines;
  - coverage improves meaningfully over exact sets.
- **KEEP IMPLEMENTATION BUT DEFAULT OFF**: the mechanism is useful, but false joins remain material
  or confidence in the threshold is insufficient. Production stays on `actor_set`.
- **REJECT ACTOR-PAIR CREATION**: actor-pair identity is fundamentally too broad even with
  semantic compatibility.

Low coverage is not failure by itself. No implementation or threshold change after seeing the
hold-out.

## Diagnostic hypotheses to test (not reasons to change anything)

- **"One close neighbour":** the 0.40 rule admits a development similar to any one member. On
  development data a Greenland/Arctic piece and a panda loan joined a US-China summit group this
  way, while at 0.50 they did not.
- **Situation persistence:** `france-pope` (a papal visit) is created by both rules. This is a
  question about what deserves a persistent Situation, separate from threshold tuning.
